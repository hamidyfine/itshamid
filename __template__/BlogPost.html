Architecture Micro-frontends

Micro-frontends without the chaos

Splitting a monolith into independently deployable frontends sounds clean on a whiteboard. Here's what actually held up in production — the boundaries, the shared contracts, and the mistakes I'd undo.

HY
Hamid Yaftian
Jun 14, 20268 min read
<mfe/>
// Four teams, four deploy pipelines, one shell that stitches them together at runtime.

Every few years someone declares the monolith dead and micro-frontends its replacement. That framing sells conference tickets, but it's wrong. Micro-frontends are an organizational tool before they're a technical one. If your teams aren't stepping on each other, you probably don't need them. If they are, no amount of clever module federation will save an architecture that ignores where the real seams sit.

At Heaptify we ran four product teams against a single React codebase. Deploys were a queue. A one-line copy change waited behind someone else's risky refactor. So we split — and here's what actually worked.

Draw boundaries around teams, not routes

The first instinct is to slice by URL: /dashboard is one app, /settings is another. That feels tidy and ages badly. Routes get reorganized; ownership doesn't. We drew boundaries around the team that owns the domain instead, and let each own whatever routes their domain touched.

A micro-frontend boundary should map to a Slack channel, not a URL prefix.

Once boundaries followed ownership, the shell's job became simple: mount the right remote for the current route and get out of the way.

The shell owns three things, and only three

Scope creep in the shell is how micro-frontend projects die. Ours was allowed to own exactly three responsibilities:

  1. Routing — deciding which remote is active for a given URL.
  2. Shared shell chrome — the nav, the auth boundary, global toasts.
  3. A tiny event bus — the one sanctioned way remotes talk to each other.

Everything else — data fetching, state, styling — lived inside the remotes. The moment the shell starts knowing about a feature's data model, you've rebuilt the monolith with extra network hops.

shell/registry.ts 
// The whole contract between shell and remotes.
export const registry = [
  { match: '/dashboard', remote: 'dashboard@/remotes/dashboard.js' },
  { match: '/budgets',   remote: 'budgets@/remotes/budgets.js' },
  { match: '/settings',  remote: 'settings@/remotes/settings.js' },
];

export function resolve(pathname) {
  return registry.find((r) => pathname.startsWith(r.match));
}

Keep the registry boring. It should read like a config file a new engineer understands in thirty seconds. If resolving a remote needs its own README, the abstraction is leaking.

Version the contract, not the components

The failure mode everyone warns you about is shared-state hell: two remotes on different React versions, a context provider that only half the tree can see. We sidestepped most of it with one rule — remotes never import each other. They import a versioned @contracts package of types and event names, and nothing else.

When a remote wanted data from another, it went through the event bus with a typed payload. Slower to write, dramatically cheaper to change. A team could rewrite their entire internals over a weekend and nobody else noticed, because the contract never moved.

What I'd undo

We over-invested in a shared component library too early. For the first six months it created more coordination than it saved — every button tweak became a cross-team negotiation. The lesson: let duplication live until the pattern is obvious, then extract. Premature sharing is just coupling with better branding.

Was it worth it?

Deploy frequency roughly tripled and the release queue disappeared. But the honest headline isn't the architecture — it's that teams stopped waiting on each other. That's the entire point. If you can get there with a well-structured monorepo and good CI, do that first. Reach for micro-frontends when the org chart, not the codebase, is the thing that's slow.
